## 一、目标重定义

| | 旧 | 新 |
|---|---|---|
| 重心 | 给隧道场景做一个能看的前端 | 真实场景 3D 建模 + 病害三维定位算法 |

**交付判据（可验证，不是口号）**

1. 输入小车视频 → 输出**带尺度、带相机轨迹**的隧道表面网格；
2. 病害在网格上有三维坐标 + 可量测几何量（长度/面积，位置可换算为桩号 + 环向角）；
3. 网页可打开该网格并定位到病害；
4. 精度有量化说明：有真值则对比真值，无真值则给自洽性检验，**并明确写出未验证的部分**。

## 二、输入现实约束（先摆事实）

| 项 | 现状 | 对算法的影响 |
|---|---|---|
| 视频 | **项目目录内暂无视频文件**（已全盘查找） | M1 之前只能用公开数据验证管线 |

| 光照 | 隧道灯带、明暗交界、局部过曝 | 匹配失效的主要来源之一 |

## 三、为什么难：写清失效机制

难点不等于「难」，要写清**怎么坏**，才能对症下药。

1. **弱纹理 + 重复纹理** — 混凝土表面特征稀少；管线、灯带、管片环缝是重复图案 → 出现大量「错误但高分」的匹配 → 轨迹被拉歪甚至整体坍缩。
2. **纯前向运动的窄基线退化** — *这是隧道最核心的困难*。小车沿轴向前进，相机几乎只沿光轴平移：视差主要来自视场外沿，中心区域三角化深度极不稳定 → 点云沿轴向「拉丝」。这也是很多室内/隧道 SfM 失败的主因，而不是「特征不够」。
3. **管状自相似 → 假回环** — 环向各角度纹理相似，回环检测可能把第 3 环认成第 30 环，直接摧毁尺度与轨迹。
4. **病害本身违背「好特征」假设** — 裂缝是细长低频结构，真实宽度可能只占亚像素；**检测得到 ≠ 定位得准**，这是本项目最容易被过度宣称的地方。

已有文献印证：隧道场景的标准做法是 SfM + MVS + **Poisson 重建 + 统计滤波**（《Tunnel 3D Reconstruction Method Based on SfM and Multi-View Stereo》, TRR 2025，明确主张单段视频即可、并给出优于基线的评价协议）；另有工作专门指出隧道/圆柱场景需**放弃特征匹配、改用几何先验**（Feature-less Stitching of Cylindrical Tunnel）。两条相互独立的信息都指向：**不要把成败押在特征匹配上**。

## 四、技术路线：三轨并行 + 交叉验证

不单押一条路线——每条都有已知失效模式，交叉验证本身也是唯一的自检手段。

### 轨 A — 显式几何主干（主心骨，可度量）

**COLMAP 4.2.0 官方 Windows CUDA 二进制**驱动（已核实可得并**已实测跑通**，见 §九）：

```
1. 特征    feature_extractor   --FeatureExtraction.type SIFT | ALIKED_N16ROT
2. 匹配    sequential_matcher  --FeatureMatching.guided_matching 1
                               --SequentialMatching.overlap 10 --loop_detection 1
3. 位姿    mapper（增量）  ←→  global_mapper（GLOMAP 全局，抗序列漂移）  双路对照
4. 滤波    point_filtering     （作用在稀疏模型上，不是 PLY）
5. 稠密    image_undistorter → patch_match_stereo → stereo_fusion
6. 网格    advancing_front_mesher（**首选**） / delaunay_mesher
           ⚠️ 不要用 poisson_mesher —— 本构建下恒输出空网格（实测 0 顶点）
7. 可选    mesh_texturer → 带纹理网格，前端直接可用
```

完整可跑脚本：**`colmap_pipeline.sh`**（本模块内，含踩坑注释；已整体实测通过）。

- 选它的理由：文献公认路线；几何**可度量**（能出断面、直径、收敛变形），这是「探伤 + 量测」类项目唯一站得住的底子。
- 已从源码核实 COLMAP 4.2 原生支持 `ALIKED_N16ROT` / `ALIKED_N32` / `ALIKED_LIGHTGLUE` / `SIFT_LIGHTGLUE`（`src/colmap/feature/aliked.cc`、`onnx_matchers.h`）。
- **ONNX 已确认可用**：官方包内带 `onnxruntime.dll` + `onnxruntime_providers_cuda.dll`。
  ALIKED **CPU 模式已实测跑通**（2000+ 特征/图）。GPU 版 ONNX 尚缺 `cublas64_12` /
  `cublasLt64_12` / `cudart64_12` / `cudnn64_9` / `cufft64_11`（官方包未捆绑）。
- ⚠️ **ALIKED 模型必须预置**：COLMAP 默认从 `github.com` 在线拉取，本机被墙会失败
  （实测 curl 56→7 三次重试后 `Failed to download file`）。已把 `aliked-n16rot.onnx` /
  `aliked-n32.onnx` 下到 `F:\data\toolchains\colmap420\bin\` 并通过 SHA256 校验，
  运行时用 `--AlikedExtraction.n16rot_model_path` 指向本地文件。

### 轨 B — 学习式几何补强（治前向退化与弱纹理）

- **VGGT**（CVPR 2025 最佳论文）：前馈一次推理出内参 + 外参 + 深度图 + 点图，秒级。
  两个用途：① 与轨 A 的位姿做**交叉验证**（两者不一致 = 有效的自检报警）；② 对 COLMAP 注册失败的帧补几何。
  ⚠️ 8 GB 显存约束 → 必须**窗口化**（分批 + 滑动窗融合），不能一次喂几百帧。
- **MASt3R / MASt3R-SLAM**（已 vendor，第一阶段就在）稠密匹配 + 局部 SLAM，对视频序列天然友好。
- ⚠️ 二者权重许可为 **CC BY-NC-SA 4.0（非商用）**，只能用于研究验证，不得进入商业交付物（见 §八）。

### 轨 C — 面元高斯渲染层（演示画质，可选）

- **PGSR**（平面化高斯）专为「平面主导」场景设计 —— 隧道内壁恰是平面主导，契合度高；
- **2DGS** 面元高斯可直接提网格。
- 定位：**让网页里「像真的」**。几何精度必须与轨 A 的 mesh 交叉比对，**不得单独作为量测依据**。
- ⚠️ 许可均为研究性（见 §八）。

### 轨 D — 探伤（CV 侧，现成资源最多）

1. **数据**：TACK TTD（隧道专用、**多类**：裂缝 / 渗水 / 泛碱，3774 张 2448×2048，HuggingFace 可下）；Tunnel200（衬砌裂缝像素掩码）；CrackSeg9k、DeepCrack（预训练基线）；SDNET2018（图像级、量大）。
2. **模型**：U-Net / DeepLab（CrackSeg9k 自带现成实现）、YOLO-seg（工程落地快）、裂缝专用 SOTA（CrackFormer 系）。
3. **接口纪律（关键、最容易踩）**：检测输出必须**反变换回原始图像像素坐标**。模型几乎都会做 resize / letterbox / 裁剪，若把「模型输入坐标系」的像素直接拿去求交，结果全错且不报错。既有 `localize_defects.py` 已强制 `coordinate_space == 'original_image_pixels'` —— **这个约束是对的，保留**。

### 融合：既有资产继续沿用

第一阶段留下的两件东西设计是正确的，不推翻、只补缺：

| 资产 | 状态 | 处置 |
|---|---|---|
| `reconstruct.py` → `scene.json`（schema v1：点云/相机/尺度/质量） | ✅ 设计正确，且明确拒绝伪造 `surface_available` | 补 mesh 字段 |

| **mesh 生产** | ❌ **缺失，管线在此断链** | **本轮抓手** |

→ 整个模块缺的只有一环：**从视频生产出可信的 mesh**。这也正是本计划的主攻方向。

## 六、尺度确定（单目必答题）

`resolve_scale()` 现有 `point_distance` / `camera_distance` 两种锚定，建议扩展：

1. **管片环宽锚定**（盾构隧道常见 1.2 m / 1.5 m —— 最可靠、最工程化）；
2. 标定板 / 已知长度基准物；
3. 轮式里程计里程（小车行驶距离）。

**不锚定 = 只有 sfm_unit**。此时一切绝对尺寸结论（裂缝宽度、净空收敛）都不成立。

### 9.4 管线上一个真实断链（**已发现并修复**）

`reconstruct.py` 导出的 `scene.json` **从来没有 `scene_id` 字段**，而 `localize_defects.py`
强制校验 `scene['scene_id']` 并与 mesh 比对 → **这两半从来就跑不通**（既有产物
`results/public_sacre_coeur/scene.json` 已确认无此字段）。

- 修法：在 `reconstruct.py` 增加 `scene_identifier()`，**由内容派生**的稳定 ID
  （对 source_kind + 相机签名 + 尺度因子 + 点数取 SHA256 前 16 位），
  同一输入重跑得到同一 ID，scene 与 mesh 自动对齐、无需人工传值。
- 新增 `mesh_io.py`：把 COLMAP 网格 PLY 转成 `localize_defects.py` 需要的 NPZ
  （`vertices` / `faces` / `scene_id`），并拒绝导出空网格。
- **实测闭环**：`scene_id = scene-435dc09c28d6d4e6` → 网格 36,314 顶点 →
  病害像素射线求交，裂缝检测 **33/33 全部命中**并给出三维坐标
  `[-2.9964, -0.0694, 4.2792]`；渗水检测 1/3 命中，状态如实标为 `partial`
  （未命中的像素不伪造坐标）。

### 9.5 负结果（留档）

1. **`poisson_mesher` 在本构建下恒输出空网格**（`vertex 0 / face 0`），
   depth 9 / 11 / 13 三种取值均如此，而输入 `fused.ply` 确实带法向。
   → 文献推荐的 Poisson 路线在 Windows 官方包上不可用，改用
   `advancing_front_mesher`（首选）或 `delaunay_mesher`。
2. **GPU 版 ONNX 不可用**：`onnxruntime_providers_cuda.dll` 依赖
   `cublas64_12` / `cublasLt64_12` / `cudart64_12` / `cudnn64_9` / `cufft64_11`，
   官方包**一个都没捆**。ALIKED 走 CPU 即可（速度够用）。
3. **COLMAP 选项命名空间不一致**（会静默跳过整步）：`FeatureExtraction.use_gpu` 是 4.x 新名，
   但特征数仍是 `SiftExtraction.max_num_features`（旧名）。用错只报
   `unrecognised option` 然后**直接不执行该步**，极易误判为"重建失败"。

## 十一、第二轮：真实隧道视频全流程实测（2026-09-29）

目标：**先用真实隧道视频把全流程跑通，精度优化留到之后**。

### 11.1 数据

| 数据 | 来源 | 说明 |
|---|---|---|
| 隧道视频 ×3 | `leven87/tunel-abnormal-detection`（GPL-3.0） | 车头视角穿越地铁隧道：`Test-2` 13.2s / `Trainingvideos_2` 27.7s / `resized` 27.4s，均 1280×720@30fps |
| 裂缝预训练权重 | `ishaan1402/crack-seg`（⚠️ **无 LICENSE**） | U-Net+SE+深监督，7.9M 参数，DeepCrack 测试集 Dice 0.866 |
| 裂缝数据/代码 | DeepCrack、CrackSeg9k、Tunnel200 | Tunnel200 **只有 notebook 无数据**；TACK TTD 镜像**只有图无掩码** |

实测抽帧：`Trainingvideos_2` 按 2 Hz 抽得 **56 帧**，清晰度（Laplacian 方差）中位 82.7。

### 11.2 该地铁序列的有效方案：global_mapper（并非所有隧道都必须使用）

同一份数据、同一套特征与匹配：

| SfM | 结果 |
|---|---|
| 增量 `mapper` | ❌ `Registering initial image pair #33 and #49` → `Discarding reconstruction due to bad initial pair` → 无模型 |
| `global_mapper`（GLOMAP） | ✅ **56/56 注册**，7,469 点，重投影 **0.80 px**，平均轨迹长 4.69 |

**匹配本身完全没问题**（502 个像对、中位 78 内点、**最高 799**）——失败纯粹来自
「前向运动下双视图三角化病态，初始像对过不了检查」。这从机理上证实了 §三-2 的判断，
也说明「把成败押在特征匹配上」是错的：**要换的是 SfM 策略，不是特征**。
`colmap_pipeline.sh` 已改为 global_mapper 优先、mapper 兜底。

### 11.3 几何合理性（自洽性检验）

- 相机轨迹沿主轴 **100% 单调**，总跨度 12.79 单位，横向抖动仅 0.227 / 0.126
  → 一条平顺的直线穿越轨迹，与「沿隧道前进」的先验一致。
- 相机到可见点中位距离约 2.14 重建单位，只是该序列内部统计，**不能据此等同于隧道半径**。小车可能不在断面中心，视线也不一定垂直内壁。不能用假定的 2.5–3 m 半径反推尺度；必须用独立测量的距离、已标定双目基线或可靠的传感器约束。当前成果保持 `sfm_unit`。

### 11.5 本轮修掉的两个真实缺陷

**① 反畸变失败导致整批中止。**`cam_from_img` 原本是「任何一个像素反畸变不收敛就整体抛异常」。
56 个相机里有 4 个（k≈-0.16）在远离主点的像素上迭代不收敛 → **一次 5.7 分钟的全量定位整个失败**。
已改为**逐像素标记** `inverse_distortion_failed`（本次 372 个像素，占 0.7%），其余像素继续求交；
新增 `usable_count`，让「管线缺陷」与「几何未命中」在统计上分开。

**② 射线求交是 CPU 瓶颈。**原来逐条射线遍历全部面片，实测 **17.8 ms/射线**，
6 万条射线要 20 分钟以上（实测跑了 7 分钟没完就被中止）。
→ 新增 `intersect_gpu.py`（torch/CUDA 分块向量化）。**实测加速 71.6×**（0.25 ms/射线），
全套定位 19.8 秒跑完。等价性经量化验证（`tests/verify_intersect_gpu.py`）：

| 指标 | 结果 |
|---|---|
| 命中/未命中判定一致率 | **100.000%** |
| 命中时的三角面 ID 相同率 | **100.00%** |
| t 相对误差（max） | 1.59e-06 |
| 交点三维偏差（max） | 5.11e-06 |

（float32 vs float64 的合理判据；三角面 ID 在共享边退化情形可能不同，实测未出现。）
顺带也把 CPU 版改成按 chunk 分块，等价性由 `tests/verify_intersect_equivalence.py` 覆盖，
但**如实说明：CPU 分块只快 1.3×** —— 瓶颈在内存带宽而非 Python 循环，真正的加速来自 GPU。

### 11.6 病害检测的域差异（必须正视）

目检叠加图后确认：预训练模型在隧道广角场景里，**主要响应管片接缝、电缆槽、站台边线、
顶部灯带等线性结构**，而不是裂缝。这是「近景裂缝训练 → 广角隧道场景」的跨域必然结果。
→ 结论：**flow 已通，但当前检测结果不能当病害结论用**。后续三件事：
① ROI 限制在内壁、排除轨道/站台/灯具等已知结构；② 在隧道数据上微调；
③ 用自研或明确许可的模型替换（当前权重无 LICENSE）。

### 11.7 网格质量：离群点是头号问题

顶点到相机轨迹的距离：中位 0.74 单位，但

| 偏离 > 1.5×中位 | > 2× | > 3× | > 5× | > 10× |
|---|---|---|---|---|
| 24.6% | 14.8% | 2.95% | 0.86% | 0.07%（最大 38 单位） |

离群点使包围盒膨胀 **4.05 倍**。→ 精度阶段的第一优先级是
**统计离群点滤波**（按轨迹半径门限，或 Open3D 的 statistical outlier removal），
而不是先调 SfM 参数。
